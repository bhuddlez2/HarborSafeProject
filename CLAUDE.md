# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Three independent applications live in one repo, on purpose — keep them that way rather than merging shared code across the boundary unless there's a concrete, simple win:

- `portal/backend/` — Laravel 13 (PHP ^8.3) API. Backs **both** the portal and the public website, and hosts the Filament staff panel (see "Staff panel" below).
- `portal/frontend/` — Next.js 16 (App Router), server mode. Just the anonymous civilian assessment flow (`app/page.js`). Every officer screen — sign-in, the officer home, the law-enforcement assessment wizard — moved into the Filament panel; the old `/login`, `/admin`, `/police` and `/police/*` URLs redirect there (`next.config.mjs`).
- `website/frontend/` — Next.js 16 (App Router), static export (`output: 'export'`). The public informational site. It reaches the Laravel API from the **visitor's browser** for two things: the feedback/resource-request forms (`src/app/lib/forms.js`) and the Events & News content (`src/app/lib/content.js`). Both go through the narrow `/api/public/*` surface and the restricted MySQL users behind it — it must never gain direct DB access. Being a static export, it has no server at runtime, so every call is client-side and `NEXT_PUBLIC_API_URL` is inlined at build time.

## Commands

### Backend (`portal/backend/`)
```
composer install
cp .env.example .env && php artisan key:generate   # first-time setup
php artisan serve                                   # dev server
php artisan test                                    # full Pest/PHPUnit suite
php artisan test --filter=testName                  # single test
php artisan test tests/Feature/SomeTest.php          # single file
php artisan migrate                                  # run migrations (default connection)
php artisan migrate --database=Portal                # run migrations against the Portal connection
php artisan migrate:all                              # custom command: creates DBs then migrates the Portal connection (app/Console/Commands/MigrateAll.php)
php artisan db:create                                # custom command: creates the Portal DB if missing (app/Console/Commands/CreateDatabases.php)
```
Filament (the `staff` panel, served from the site root — sign-in at `/login` — `app/Providers/Filament/StaffPanelProvider.php`) and Shield are installed — see `Filament_CMS_Design.md`:
```
php artisan make:filament-resource ModelName         # generate a panel resource
php artisan shield:generate                          # regenerate permissions after adding resources
```
**Never run `php artisan shield:setup` here.** It runs a bare `migrate` on the default (unreachable) `mariadb` connection, and `--fresh` drops tables through it. Shield/spatie were installed by publishing manually (`vendor:publish --tag=filament-shield-config`, `--tag=permission-config`, `--tag=permission-migrations`), pointing the migration at `Portal`, migrating, then `shield:install staff` — see `Filament_CMS_Design.md` §3.3.
**Laravel 13 requires PHP ^8.3, so XAMPP for Windows cannot run this project** — it ships PHP 8.2.12 at most. On Windows, PHP is installed separately from XAMPP (which is then used only for MariaDB); see `PORTAL_SETUP.md`. Filament also requires `ext-intl`, without which `composer install` refuses to resolve; a standalone Windows PHP needs seven extensions enabled by hand (`curl`, `fileinfo`, `intl`, `mbstring`, `openssl`, `pdo_mysql`, `zip`) plus `extension_dir`, since the zip ships no `php.ini` at all. On Fedora/Debian `intl` is a separate package.
`composer test` runs `artisan config:clear` then `artisan test`. The `vite`/`laravel-vite-plugin` setup **does** matter now: it compiles the staff panel's custom theme (`resources/css/filament/staff/theme.css`, the `->viteTheme()` in `StaffPanelProvider`). Run `npm install && npm run build` in `portal/backend` before using the panel (the `npm install` also fetches the Chromium that `spatie/browsershot` drives for assessment PDFs — Node must be present wherever the backend runs), and again after changing the theme or the panel's Blade views (Tailwind only emits classes it finds in them); `npm run dev` recompiles live. The rest of the app is a JSON API.

**`php artisan test` should pass in full — any failure is real.** `tests/Feature/ExampleTest.php` is a boot smoke test against `/up`, Laravel's built-in health route (`bootstrap/app.php`). It used to be Pest's stock scaffold asserting `GET /` returns 200, which failed for months because `/` is the staff panel's root and redirects an anonymous visitor to `/login` (a 302); don't point it back at `/`. What `/` does is tested in `ContentPagesRenderTest`.

### Portal frontend (`portal/frontend/`) and website frontend (`website/frontend/`)
Same script names in both, run from within each directory:
```
npm install
npm run dev      # dev server
npm run build    # next build (website/frontend exports fully static; portal/frontend does not — see next.config.mjs)
npm run lint      # eslint
```
No test runner is configured in either frontend's package.json.

### End-to-end tests (repo root)
```
npm install
npx playwright test              # runs tests/*.spec.js against website/frontend (see playwright.config.js)
npx playwright test -g "name"    # run tests matching a title
```
Playwright's `webServer` boots `website/frontend` only (`npm run dev --prefix website/frontend`, or `serve website/frontend/out` in CI) — it does not exercise the portal or the backend.

**Root `package.json` is not a runnable app.** It declares `next` as a dependency and has `dev`/`build`/`start` scripts left over from before the repo was split into `website/frontend` and `portal/frontend`, but there's no `app/`/`pages/` directory at root — those scripts don't work. Root's real jobs are hosting the shared ESLint flat config (`eslint.config.js`, which lints both frontends and the Playwright specs together) and the Playwright config/tests. Use `npm run lint` at root only if you want the combined lint pass; otherwise lint from inside the specific frontend you're changing.

**That vestigial root `next` dependency has teeth, and both frontends now pin `turbopack.root` because of it.** `next` brings `postcss@8.4.31` with it, so `npm install` at the repo root — which you need for Playwright — plants an old postcss *above* both frontends. With three `package-lock.json` files in the tree, Turbopack picks the outermost as its project root, so each frontend's `postcss.config.mjs` could then resolve that 8.4.31 instead of its own 8.5.x, and Tailwind v4's `@tailwindcss/postcss` fails to instantiate. `npm run dev` dies on `globals.css` with "Error evaluating Node.js code … the module factory is not available", which blames a stale browser cache and is nothing of the kind — and `npm run build` is unaffected, so the two disagree. Each `next.config.mjs` now sets `turbopack: { root: <its own directory> }`, which fixes resolution and silences Next's "inferred your workspace root" warning. Don't remove those pins. Recovering from an already-poisoned cache needs the dev server stopped (Windows file locks, and it leaves orphaned `.next/dev/build/postcss.js` workers behind) and `.next` deleted. Dropping `next` from the root `package.json` would remove the cause outright — `eslint.config.js` only needs `@next/eslint-plugin-next`, not `next` itself — but it churns the root lockfile, so it hasn't been done unilaterally.

## Architecture

### Backend: one Laravel app, four MySQL/MariaDB connections
`config/database.php` defines `mariadb` (default — the connection stock Laravel tables were *intended* for), `Portal` (the app's actual business data), `Feedback` (full access to the website's feedback/resource-request forms and their lookup tables), and `FeedbackPublic` (same physical database as `Feedback`, meant for a restricted, INSERT-only-on-submissions MySQL user — see `Schema_Reference.md` for the exact grants — used by the public submission endpoint once it exists, not by Eloquent models). In practice, **every table including `users` currently lives on the `Portal` connection** — migrations were originally run with `--database=Portal`, which overrides the connection for any migration that doesn't set its own, and `User.php` now explicitly declares `protected $connection = 'Portal'` to match that reality (it didn't used to, which would have made any real login attempt query the wrong, unreachable `mariadb` connection). Every Portal-connection model extends `BaseModel` except `User` (which extends Laravel's `Authenticatable` but still declares `$connection` manually) — `BaseModel` throws at boot time if a subclass omits `$connection`, so that mistake surfaces immediately rather than silently querying the wrong database. When adding a new Portal-connection model, follow the existing pattern (extend `BaseModel`, set `$connection`, use `HasUuids` with a `uniqueIds()` override for the uuid-keyed tables — primary keys here are custom-named, e.g. `AssessmentDocID`, `DocumentID`, `SubmissionID` — not `id`; the auto-increment tables like `users`/`agencies`/`law_enforcement_agents` don't need that).

A fifth and sixth connection exist: `Content` (events, newsletters, event categories and `content_files`, the uploaded-file blobs) and `ContentPublic` (same physical database, intended for a restricted SELECT-only user that **does not exist in any environment yet** — see `Filament_CMS_Design.md` §6.5). `Content` is live and migrated, and the public read endpoints (`GET /api/public/events` and `/newsletters`) query through `ContentPublic` — which currently carries root credentials, so creating the SELECT-only user is a `.env` change with no code change. Note for anything touching spatie/laravel-permission: it has no documented connection setting and defaults to the `mariadb` connection, which is exactly the unreachable one described above. It's pointed at `Portal` via its migration (`*_create_permission_tables.php`) and the local subclasses `App\Models\Role` / `App\Models\Permission` (set in `config/permission.php`) — always use those, never `Spatie\Permission\Models\*` directly.

**See `Schema_Reference.md` at the repo root for the full current schema** (ER diagram + table-by-table notes) — it's kept in sync with `database/migrations/*.php` and is much easier to read than the migration files themselves. Regenerate it after schema changes rather than trusting this file's prose to stay current.

**Always migrate with `--database=Portal`, regardless of what a migration actually targets.** Portal's `migrations` table is the single canonical ledger for every migration in this project, even ones whose `Schema::connection('Feedback')->...` call routes their DDL elsewhere. Running `migrate --database=Feedback` (or any other) against a database whose own `migrations` table is empty makes Laravel try to replay the *entire* migration history into it, not just the ones meant for that database — this happened once while building the Feedback schema and had to be cleaned up.

**Time zones: store UTC, show Eastern** (`App\Support\Timezones`). The app is UTC (`config/app.php`) and every database connection is pinned to UTC (`'timezone' => '+00:00'` in `config/database.php`, deliberately not an env value), so MariaDB's `NOW()` / `useCurrent()` and Laravel's `now()` agree on every machine — before that pin, the database used each developer's own time zone and the same moment was stored differently on different machines. Anything shown to a person converts to `Timezones::DISPLAY` (America/New_York): `->timezone(Timezones::DISPLAY)` on a Filament `dateTime` column/entry or `DateTimePicker`, `->setTimezone()` on a hand-formatted Carbon (`ChangeHistory`, the assessment-record view). **Never on date-only values** (dates of birth, issue dates): Filament's `->date()` converts too and would show the day before. Date filters turn a picked Eastern day into a UTC range (`Timezones::dayStartUtc()`/`dayEndUtc()`, used by `AssessmentFilters::dateRange()`). Event `starts_at`/`ends_at` are `DATETIME` and already followed this rule. Migration `2026_10_08_140000_restore_utc_for_timestamps_written_by_laravel` repaired values Laravel wrote under the old per-machine session (run it right after pulling the change). `TimezoneTest` covers it.

**Migrations vs. the live dev database can drift.** Laravel's `migrations` table only tracks which migration *files* have run by name; editing an already-applied migration's contents doesn't retroactively change a database that was migrated before the edit. If you change a migration that has already run somewhere, that environment needs a deliberate `migrate:fresh --database=Portal` (or a new migration), not just a re-run of `migrate`. This bit the project once already — the dev database was rebuilt from scratch to match the migration files, and as of this schema pass it's confirmed reconciled — but it's a recurring risk any time an already-applied migration gets edited, not a one-time fix. If in doubt, check with `php artisan migrate:status --database=Portal` rather than assuming the live schema matches `database/migrations/*.php`.

### The assessment tables are linked, not independent
Two parallel assessment paths share the same `_assessment_answers` table (11 risk-indicator booleans): `PrivateAssessment` (public/anonymous submissions, `belongsTo` `SubmitterInfo` via `SubmissionID` for optional contact info) and `LawEnforcementAssessment` (authenticated law-enforcement submissions, `belongsTo` `User` via `submitted_by`). See `Schema_Reference.md` for the full relationship diagram. **The civilian flow** is `portal/frontend/app/page.js` → `submitAssessment()` in `app/lib/api.js` (the only function left there): it POSTs risk answers to `/api/assessments`, optionally submitter info to `/api/submitter-info`, then the offender/victim record to `/api/private-assessments`. **The law-enforcement flow** is the Filament page `App\Filament\Pages\NewAssessment` (`/police/new-assessment`), which creates the `AssessmentAnswers` row and the `LawEnforcementAssessment` row itself, in one `Portal` transaction, with `submitted_by = auth()->id()` — no API round trip. Its question wording is duplicated in `NewAssessment::QUESTIONS` and `portal/frontend/app/lib/lethality-questions.js`; change both together. Watch the response shapes: `/api/assessments` wraps the created record in `{ data: ... }`, but `/api/law-enforcement-assessments` returns it bare. If you touch field names on any assessment-related table, update the migration, the model's `$fillable`, the controller validation rules, the `NewAssessment` wizard fields, and the civilian frontend payload together — they've fallen out of sync with each other more than once.

### Auth: Filament login, route-level auth and one model policy exist; Shield permissions do not
`users` has `role` (a native `App\Enums\UserRole` enum: `law_enforcement`/`secretary`/`admin`/`police_admin`, cast — not a raw string), `is_active`, `first_name`/`last_name` (50 characters each, the source of truth for a person's name) alongside `name` (kept as a real column because tables search and sort on it, and always rebuilt as "First Last" by `User::booted()` — never write it directly), and Fortify-style 2FA columns that **nothing uses** — Fortify isn't installed, and Filament's built-in MFA expects its own column names (`app_authentication_secret`, `app_authentication_recovery_codes`); `law_enforcement_agents` holds badge/agency data for officers *and* police admins (1:1, keyed by `user_id`; `User::officerIdentity()` reads it with the agency name, `User::agencyId()` reads just the agency — a police admin's row exists purely to carry that link); `law_enforcement_assessment.submitted_by` is a real FK to `users.id`. **Sign-in is Filament's login** at `/login` (`App\Filament\Pages\Auth\Login`, Filament's authentication with the old Next.js page's look), gated by `User::canAccessPanel()` (`is_active` plus a valid role); each panel page gates itself with `canAccess()` on `role`. On the API, the law-enforcement, agent and agency routes and every non-`store` action on the civilian tables sit behind `auth:sanctum` (see Routing). `LawEnforcementAssessmentController::store()` requires a `law_enforcement` user (403 otherwise) and sets `submitted_by` from `$request->user()`, ignoring the body. **In the panel, law-enforcement assessments are governed by `App\Policies\LawEnforcementAssessmentPolicy`** (registered with `Gate::policy()` in `AppServiceProvider`): hand-written, `users.role` plus `submitted_by` ownership plus the police admin's agency, no spatie calls. Every write method returns `false` except `update()`, which allows the submitting officer. **Every edit goes through `App\Services\AssessmentEditor`**, which writes one `assessment_edits` row (who, when, required reason) plus one field-level row per changed column in `assessment_change_log` / `assessment_answer_change_log`, in one `Portal` transaction. `LawEnforcementAssessment` and `AssessmentAnswers` throw on any `update()` outside the editor (`EditedOnlyThroughAssessmentEditor`), and the edit and log models are append-only (`AppendOnly`) — so test cleanup and any other removal must use the query builder, never Eloquent deletes. Who sees which rows is the `LawEnforcementAssessment::visibleTo($user)` query scope — admin everything, police admin its own agency's officers' submissions (nothing without an agency), officer its own — and the policy's `view()` and both assessment screens' `getEloquentQuery()` all go through it. **Police admins are agency-scoped. Never widen police_admin to see all agencies or add a screen that skips LawEnforcementAssessment::visibleTo(). See Filament_CMS_Design.md §5 rule 5.** `LawEnforcementAssessmentResource` is listed in `resources.exclude` in `config/filament-shield.php` — **never run `shield:generate` for this model or remove that exclusion**, or Shield replaces the policy with a permission-based one. `OfficerAccountResource` (police admins provisioning their own agency's officers) is excluded there too, for the same reason: it authorizes itself rather than through a `UserPolicy`. **Not built yet:** Shield permissions and policies for anything else — and the API does not use this policy, so it has no per-record ownership checks (`update()` on that controller still accepts `submitted_by` from any authenticated caller), and nothing issues Sanctum tokens (`User` has no `HasApiTokens`; `statefulApi()` is off), so in practice no client can call the `auth:sanctum` routes today.

The old placeholder Next.js login (`app/api/auth/login/route.js`, which accepted any credentials and set `session=dev-token`) and `proxy.js` are deleted — don't resurrect either.

Shield + spatie/laravel-permission are the decided authorization layer — see `Filament_CMS_Design.md`. `submitted_by` is what "law enforcement sees only their own submissions" checks against, and `role` is what coarse panel/navigation gating switches on.

### Staff panel (Filament) — officer screens and content management built
Every staff dashboard lives in one Filament v5 panel inside `portal/backend`, behind Filament's own login. Only the anonymous civilian flow (`portal/frontend/app/page.js`) stays in Next.js. Four sidebar groups (Police Admin is described with the Officer Portal below), each with its own address space:

- **Content management** (admin, secretary) — three Filament **clusters**, which render their resources as tabs across the top of each page: `Content` (`/content/{events,newsletters,categories}`), `Submissions` (`/submissions/{service-feedback,resource-requests}`, statements from the public, so **never edited** — resource requests are read-only, and service feedback's one addition is **New feedback form**, for admin and secretary to fill a form in themselves (typically one that arrived on paper, though the screen deliberately never says so): validated by `ServiceFeedbackStoreRequest::fieldRules()` (the website's own rules), saved by `ServiceFeedback::recordStaffEntry()` with `Source = staff` (shown as a "Staff" badge), `EnteredBy` and the date and time entered, plus an optional scan stored in `feedback_scans` and served only to admin/secretary by `FeedbackScanController`, never through `/files/{file}`; a mistyped entry is deleted and re-entered, and its scan goes with it — `StaffFeedbackEntryTest`. the form's date-and-time field is entered in Eastern and saved as UTC, like everything else — see **Time zones** below) and `Form options` (`/form-options/{services,resource-types,counties}`, the dropdown choices behind the public forms, sharing one `LookupResource` base). Plus `Accounts` (`/accounts`, `Resources/StaffAccounts/`, **admin only**): admin creates, edits and deactivates **secretaries**, never any other role and never itself. Who may manage which roles lives in one place, `StaffAccountResource::manageableRoles()` — extend that map for the planned super admin rather than adding checks elsewhere. The role is forced on create and never written on edit; nothing is deleted.
- **Assessments** — three read-only pages, with different audiences: `Assessment review` (`/assessment-review`) for law-enforcement submissions — admin sees all of them, police_admin only its own agency's — `Civilian assessments` (`/civilian-assessments`, **admin only**) for submissions from the public civilian flow, and `Change log` (`/assessment-changes`, `Resources/AssessmentEdits/`, admin and police_admin) listing every edit to a law-enforcement assessment, one row per save, scoped through `LawEnforcementAssessment::visibleTo()` like the assessments themselves. Each law-enforcement assessment row (here and in My Assessments) has a **Change log** button left of View, opening that record's history in its own pop-up (purple when the record has been edited, light gray and disabled when it hasn't — the gray is a `.fi-disabled` rule in `theme.css`), and an Amended badge — both from `App\Filament\Assessments\ChangeHistory`, with labels from `App\Support\AssessmentFields`. **Both law-enforcement assessment tables take their columns from one class, `App\Filament\Tables\AssessmentColumns::for()`**: Submitted · Officer (Assessment review only) · Victim · Offender · Relationship · Yes · Status, then the Change log, View and (My Assessments only) Edit buttons — `AssessmentTableColumnsTest`. **Both law-enforcement assessment tables (My Assessments and Assessment review) take their filters from one class, `App\Filament\Tables\AssessmentFilters::apply()`** — a filter card above the table in three columns, folded away behind a Filters button until opened (`FiltersLayout::AboveContentCollapsible`, to keep the top of the page uncluttered), deferred (nothing applies until its **Apply** button, with Reset beside it), persisted in the session. Filters: date submitted and victim/offender first and last name on both; submitting officer and agency on Assessment review only — agency for active admins only, decided by `users.role` (`hasActiveRole(UserRole::Admin)`), never the Shield `super_admin` role. Names are case-insensitive partial matches with `%`/`_` taken literally. Sex, relationship and risk-answer filters were tried and removed by team decision; the safe phone number is deliberately not filterable. Every dropdown's options are scoped through `LawEnforcementAssessment::visibleTo()` like the rows, so a police admin is never offered another agency's officers or agencies. Any future assessment table must use it; `tests/Feature/Staff/AssessmentFiltersTest.php` enforces it. The Change log's card is `App\Filament\Tables\ChangeLogFilters` (built on `AssessmentFilters`' public helpers, scoped through `AssessmentEdit::visibleTo()`): changed by, original submitter, date changed (`EditedAt`), agency (admin only) and victim/offender names matched on the assessment — never on the logged old/new values; `ChangeLogFiltersTest` enforces it. **Keep the history out of the View pop-up:** View shows the current record only, complete on its own, so an export from it is the whole current document with nothing interleaved or apparently missing (asserted in `AssessmentChangeLogTest`). That export exists: View's **Download PDF** button (both law-enforcement tables) hits `GET /assessments/{id}/pdf` (`AssessmentPdfController`, rendered by Browsershot from `resources/views/filament/pdf/assessment.blade.php`). That route is outside the panel, so the controller looks the record up through `LawEnforcementAssessment::visibleTo()` itself — never fetch it unscoped (`AssessmentPdfAccessTest`). Neither offers edit; the civilian one offers no delete either, since a danger assessment is a safety record rather than something to tidy up. Most civilian submissions are anonymous — `_private_assessment.SubmissionID` is nullable and the flow only collects contact details when someone submits for another person *and* declines anonymity — so a null submitter is the normal case, not missing data. `VictimSafePhoneNumber` is kept out of both tables and shown only in the detail view.
- **Officer Portal** (law_enforcement, police_admin — *not* admin) — Home (`Pages/Police.php`, slug `police`), New assessment (the LAP wizard, officers only), My Assessments (`Resources/LawEnforcementAssessments/`, at `/police/assessments` — a list with View and Edit pop-ups, **officers only**, each seeing and editing their own submissions: details and the 11 answers, with a required reason, saved through `AssessmentEditor`; it replaced the old `Pages/MyAssessments.php` mockup), Account. Search Records, once a "Coming soon" placeholder, was removed: filtering on the assessment tables replaces it. Police admins and admins are kept out of My Assessments by the resource's own `canAccess()` and review submissions in `Assessment review` instead; the Home page's "past assessment" link (`Police::pastAssessmentsUrl()`) sends police admins there. `LawEnforcementAssessmentPolicy` still lets admin and police admins *view* records (admin all, police admin own agency), because `Assessment review` shares that policy for its View action — narrow the policy and the review screen breaks. A separate **Police Admin** group holds Officers (`Resources/OfficerAccounts/`, `/police/officers`): a police admin with an agency lists, creates and edits that agency's officer accounts only (`User::managedAgencyId()`), never deletes them. Both account screens, and the Account (profile) page via `App\Filament\Pages\Auth\EditProfile`, take first and last name as separate fields. For local data, `LocalStaffUserSeeder` creates one login per role plus a second officer, and a second agency ("Second Test PD": `police-admin2@`, `officer3@`) so the agency scope can be tried, and `LocalAssessmentSeeder` gives each officer two assessments (both local-only, idempotent, run with `--database=Portal`, neither registered in `DatabaseSeeder`).

**Police admins get a single "Police Admin" sidebar group** — Home, Assessment review, Change log, Officers, Account, in that order — while every other role keeps its own groups. The shared items pick their group and sort by role through `App\Filament\PoliceAdminNavigation` (the one place that order lives); `tests/Feature/Staff/NavigationTest.php` pins each role's sidebar.

**Clusters must be registered with `->discoverClusters(...)`** in `StaffPanelProvider`; an unregistered cluster resolves as a class but registers no routes, so every resource inside it 404s. A cluster root redirects to the first tab the user can open (`Cluster::mount()`), and hides itself when every resource inside refuses the user.

Still not built: a super admin role that creates police admins, admins and agencies (until then those come from `LocalStaffUserSeeder` locally), Shield permissions, model policies beyond `LawEnforcementAssessmentPolicy` (hand-written on role + `submitted_by` + the police admin's agency, registered in `AppServiceProvider`, and excluded from Shield in `config/filament-shield.php` so `shield:generate` can't overwrite it), and view logging (the officer Home still says views are logged; nothing does).

**Required and optional inputs are marked the same way in all three apps:** a red asterisk after a required field's label, and faded grey "Optional" ghost text (the placeholder) inside an optional text input, text area or dropdown. A date can't hold ghost text, so an optional date that needs flagging (the offender's date of birth, in the wizard, the officer edit pop-up and the civilian flow) gets the same grey "Optional" after its label — `RequirementMarkers::optionalLabel()` in the panel, `OptionalMark` in the civilian flow. Nothing on uploads, toggles or checkboxes. In the panel that is Filament's own asterisk plus `App\Filament\Forms\RequirementMarkers`, registered in `AppServiceProvider` as a default for every `TextInput`/`Textarea`/`Select` outside table filter cards — so never give an optional field its own `->placeholder()` (put examples in `->helperText()`), never add `markAsRequired(false)` (the sign-in page is the one exception), and give conditionally-required fields such as a confirm-password box an explicit placeholder. `RequirementMarkers::OPTIONAL` / `RequirementMarkersTest` cover it. The website's version is `requirement` on `Field` plus `OPTIONAL_PLACEHOLDER`/`selectClass` in `website/frontend/src/app/components/FormControls.js`; a one-of-several group (the email/phone pair on Contact) puts the asterisk and "At least one of these is required" on its legend instead. The civilian flow (`portal/frontend/app/page.js`) has its own `RequiredMark`/`OPTIONAL_PLACEHOLDER`.

**Table columns line up by kind** (`App\Filament\Tables\TableAlignment`, roadmap Phase K): text — dates, names, titles, emails — is left-aligned with its heading (Filament's default, so no alignment call); symbols — yes/no icons and badges — are wrapped in `TableAlignment::symbol()`, which centres them and marks the header so `theme.css` centres them under the heading's *words* rather than words plus sort arrow. Applied to the content-management tables, Civilian assessments and Accounts, enforced column by column in `TableAlignmentTest`. The police-side tables (Assessment review, My Assessments, Officers, Change log) are being aligned separately by Tyler and still centre everything.

The panel's look (dark sidebar, `#5C0F8B`, Tailwind gray, Nunito/Montserrat, no topbar, no dark mode) comes from the custom theme plus `StaffPanelProvider`; `SESSION_LIFETIME` is 15 in `.env.example` because the officer Home promises a 15-minute lock — but check your own `.env`, which has been seen at 120, and note that it is an *idle* timeout, not a re-auth on every navigation (see `Filament_CMS_Design.md` §12). Four roles: `law_enforcement` (own submissions only, the only role that may edit a submitted assessment), `police_admin` (provisions its own agency's officer accounts, views its own agency's law-enforcement submissions and change logs, edits nothing), `secretary` (content and submissions, never assessment PII), `admin` (edits content and the public forms' dropdown options, views submissions, views **all** civilian and law-enforcement assessments, creates **secretaries only** — **not** the officer portal, never officers, never edits an assessment; admin is deliberately not a superset). Police admins and admins are to be created by a planned super admin role only.

**Sign-in and landing.** Everyone sees the same login screen at `/login`, a neutral address at the site root shared by every role (the panel is served from the root; old `/staff/...` links redirect to their new address via `routes/web.php`). Where they land is decided in exactly one place, `App\Filament\StaffLanding` — admin/secretary to content management, officers/police admins to the officer portal — consulted by both `StaffLoginResponse` (after sign-in) and `RedirectStaffHome` (opening `/staff` directly). Don't reach for `$panel->homeUrl()`: it only sets the sidebar brand link and does not affect either redirect.

**Uploads are database rows, not files on a disk.** Event images and newsletter PDFs live in `content_files` on the `Content` connection, written through `App\Filament\Forms\Components\DatabaseFileUpload` and served by `ContentFileController` — publicly at `/api/public/content-files/{file}` (only while a *published* event or newsletter points at the file) and to staff at `/files/{file}`. Two rules to respect: `App\Models\ContentFile` has a global scope excluding the `contents` blob from every query (use `->contents()` for the bytes, never the attribute), and uploads are capped at 4 MB (images) / 8 MB (PDFs) because `max_allowed_packet` is 16 MB and caps a single row in both directions. **Those caps need php.ini to cooperate** — stock `upload_max_filesize` is 2M, which makes PHP discard the file before Laravel runs, so the failure looks like a broken panel rather than an oversized file; this project needs `upload_max_filesize = 8M` and `post_max_size = 12M` (`PORTAL_SETUP.md`). `DatabaseFileUpload::effectiveLimitKb()` clamps the advertised limit to whatever PHP will actually accept, so the helper text cannot over-promise. `events.image_path` / `newsletters.file_path` are kept but unused, so a move to R2/B2 stays a config change.

**See `Filament_CMS_Design.md` at the repo root** for the full design: the verified version matrix, the prerequisites (`ext-intl` and spatie's default-connection trap — `storage:link` is no longer one), the complete access matrix, the `Content` connection schema including `content_files`, the navigation layout (§13), and the ordered implementation phases with verification gates. Done: Phases 1–6, 8 (content management), 10 (public content API and website cutover), 11 (officer screens and wizard) and 12 (Next.js cleanup); 7 and 13 partly.

**The access matrix is enforced by test.** `tests/Feature/Staff/PanelAccessTest.php` writes §5 out as a table and asserts each role reaches exactly its own row — it exists because `Police`, `MyAssessments` and `SearchRecords` (since removed) had all quietly granted `admin`, which put the whole Officer Portal in an admin's sidebar. If you change who sees what, that file is the place it has to agree. Two gotchas for authenticated tests: cleanup sweeps on the fixed `peststaff` prefix (so a fatal-killed run self-heals, but don't run these in parallel), and `UploadedFile::fake()` is unusable here — `fake()->image()` needs GD, which isn't installed, and `fake()->create()` writes zero bytes while reporting a size. Use `Illuminate\Http\Testing\File` with a real `tmpfile()`.

### Routing
`bootstrap/app.php` only registers `routes/web.php`, `routes/api.php`, and `routes/console.php`. `routes/api.php` uses `Route::apiResource(...)` for `/assessments`, `/private-assessments`, `/submitter-info`, `/law-enforcement-assessments`, `/law-enforcement-agents`, and `/agencies` — the naming is a little counterintuitive: `/api/assessments` is the risk-indicator table (`AssessmentAnswers`), and `/api/private-assessments` is the offender/victim PII table (`PrivateAssessment`). Only `store` on the three civilian tables (`/assessments`, `/private-assessments`, `/submitter-info`) is public, because the anonymous civilian flow needs it; their other actions, and every action on the three law-enforcement tables, are behind `auth:sanctum`. Separately, a `Route::prefix('public')` group exposes a deliberately narrow surface for the public website: `GET /api/public/{services,resources,counties}` and throttled (`throttle:10,1`) `POST /api/public/{service-feedback,resource-requests}`. Those controllers route through the restricted `FeedbackPublic` connection, never the full-access `Feedback` one. Also in that group: `GET /api/public/events` and `GET /api/public/newsletters`, which serve published website content shaped by `PublicEventResource` / `PublicNewsletterResource` to match what the Events & News page consumes — **those two resources are the contract**, asserted key-for-key in `tests/Feature/Public/ContentEndpointsTest.php`, and `website/frontend/src/app/lib/content.js` has to change with them. Both read through `ContentPublic`; `PublicEventController` joins `event_categories` rather than eager-loading it, because a relation resolves on the *related* model's connection (`Content`) and would bypass the restricted user. Plus `GET /api/public/content-files/{file}`, which streams an event image or newsletter PDF out of the database — and only while a *published* record points at it, since `content_files` has no published flag of its own to consult. Its staff-side twin is `GET /files/{file}` in `routes/web.php`, which is guarded by `App\Http\Middleware\EnsureStaffPanelAccess` rather than `auth`: Laravel's `auth` redirects to a route named `login` that doesn't exist here (sign-in is Filament's), so `auth` would turn an anonymous request into a 500. The same middleware guards `GET /assessments/{id}/pdf` (see Staff panel). No API routes for the change log — it is read in the staff panel only (`/assessment-changes` and each record's View pop-up). The staff panel is served from the site root (Filament registers its routes itself): sign-in at `/login`, content management under `/content`, `/submissions` and `/form-options`, the officer portal under `/police`, and `/` sending a signed-in user to their own area. Everything under `/api` is the JSON API, not the panel; `/staff/{path}` in `routes/web.php` redirects old links. The panel id is still `staff`, so route names stay `filament.staff.*`.
