# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Two independent applications live in one repo, on purpose — keep them that way rather than merging shared code across the boundary unless there's a concrete, simple win:

- `portal/backend/` — Laravel 13 (PHP 8.4.1 or newer — see below) API. Backs the public website, and hosts the Filament staff panel (see "Staff panel" below), which serves every staff and officer screen itself. (A third app, `portal/frontend/`, held the civilian assessment until it moved to the website; it is gone.)
- `website/frontend/` — Next.js 16 (App Router), static export (`output: 'export'`). The public informational site, including the civilian lethality assessment (`src/app/assessment/`, linked from Get Support, where the client chose to put it; keep it there). It reaches the Laravel API from the **visitor's browser** for three things: the feedback/resource-request forms (`src/app/lib/forms.js`), the Events & News content (`src/app/lib/content.js`) and the civilian assessment (`src/app/lib/assessment.js`). All go through the narrow `/api/public/*` surface and the restricted MySQL users behind it — it must never gain direct DB access. Being a static export, it has no server at runtime, so every call is client-side and `NEXT_PUBLIC_API_URL` is inlined at build time.

Filament Shield and spatie/laravel-permission were installed once and **removed on 2026-10-24 without ever being used** (no role or permission was ever created); migration `2026_10_24_120000` dropped their five empty tables. Don't reinstall them: who may do what is decided in code by developers only, on purpose (see Auth).
**This project needs PHP 8.4.1 or newer, so XAMPP for Windows cannot run it** — it ships PHP 8.2.12 at most. Laravel 13 itself asks for 8.3, but the locked Symfony 8 packages need 8.4.1, and `composer.json` pins `config.platform.php` to `8.4.1` so a `composer update` on a newer PHP can never lock packages the server can't run. Raise that pin only when every server is on the newer PHP. On Windows, PHP is installed separately from XAMPP (which is then used only for MariaDB); see `PORTAL_SETUP.md`. Filament also requires `ext-intl`, without which `composer install` refuses to resolve; a standalone Windows PHP needs seven extensions enabled by hand (`curl`, `fileinfo`, `intl`, `mbstring`, `openssl`, `pdo_mysql`, `zip`) plus `extension_dir`, since the zip ships no `php.ini` at all. On Fedora/Debian `intl` is a separate package.
`composer test` runs `artisan config:clear` then `artisan test`. The `vite`/`laravel-vite-plugin` setup **does** matter now: it compiles the staff panel's custom theme (`resources/css/filament/staff/theme.css`, the `->viteTheme()` in `StaffPanelProvider`). Run `npm install && npm run build` in `portal/backend` before using the panel, and again after changing the theme or the panel's Blade views (Tailwind only emits classes it finds in them); `npm run dev` recompiles live. The rest of the app is a JSON API.

**PDFs are pure PHP (dompdf), and Node is build-time only.** The production host is IONOS shared hosting: PHP 8.4, no Node, no Chrome and no way to run binaries. So Browsershot/Puppeteer were removed, and every PDF prints through `App\Support\HtmlPdf` (`dompdf/dompdf`, used directly without the Laravel wrapper). It was chosen over mPDF for a 9 MB install against 93 MB, closer rendering of our templates, and similar memory. Rules:
- Remote loading, PHP and JavaScript are off, and every protocol is refused, so nothing is fetched or read while printing (`PdfRenderingTest` runs a throwaway server to prove it).
- The only font is the bundled DejaVu Sans, since Helvetica lacks most accented letters. Work files go in `storage/framework/dompdf`.
- dompdf is CSS 2.1: no flexbox, grid or `gap`. `table-layout: fixed` ignores column widths, `<col>` is ignored, floats break inside table cells, side padding is added to a width whatever `box-sizing` says, and **a table row can't split across pages**: anything taller than a page runs off the bottom and is lost.
- `resources/views/filament/pdf/record.blade.php` re-lays the View pop-up's own partial with CSS 2.1, so the screen and PDF share one source of content. A partial markup change needs a look at the PDF too.
- The feedback list prints in 25-row tables, with headings and page numbers drawn on each page and long comments split across rows (`ServiceFeedbackExport`). One 500-row table needed about 125 MB.

Only the website build and the panel theme build need Node, on a developer machine.

**`php artisan test` should pass in full — any failure is real.** `tests/Feature/ExampleTest.php` is a boot smoke test against `/up`, Laravel's built-in health route (`bootstrap/app.php`). It used to be Pest's stock scaffold asserting `GET /` returns 200, which failed for months because `/` is the staff panel's root and redirects an anonymous visitor to `/login` (a 302); don't point it back at `/`. What `/` does is tested in `ContentPagesRenderTest`.

**Root `package.json` is not a runnable app.** It declares `next` as a dependency and has `dev`/`build`/`start` scripts left over from before the repo was split into `website/frontend` and `portal/frontend`, but there's no `app/`/`pages/` directory at root — those scripts don't work. **That vestigial root `next` dependency has teeth, and `website/frontend` pins `turbopack.root` because of it.** `next` brings `postcss@8.4.31` with it, so `npm install` at the repo root — which you need for Playwright — plants an old postcss *above* the website. With more than one `package-lock.json` in the tree, Turbopack picks the outermost as its project root, so the website's `postcss.config.mjs` could then resolve that 8.4.31 instead of its own 8.5.x, and Tailwind v4's `@tailwindcss/postcss` fails to instantiate. `npm run dev` dies on `globals.css` with "Error evaluating Node.js code … the module factory is not available", which blames a stale browser cache and is nothing of the kind — and `npm run build` is unaffected, so the two disagree. Its `next.config.mjs` sets `turbopack: { root: <its own directory> }`, which fixes resolution and silences Next's "inferred your workspace root" warning. Don't remove that pin. Recovering from an already-poisoned cache needs the dev server stopped (Windows file locks, and it leaves orphaned `.next/dev/build/postcss.js` workers behind) and `.next` deleted. Dropping `next` from the root `package.json` would remove the cause outright — `eslint.config.js` only needs `@next/eslint-plugin-next`, not `next` itself — but it churns the root lockfile, so it hasn't been done unilaterally.

## Architecture

### Backend: one Laravel app, four MySQL/MariaDB connections
`config/database.php` defines `mariadb` (default — the connection stock Laravel tables were *intended* for), `Portal` (the app's actual business data), `Feedback` (full access to the website's feedback/resource-request forms and their lookup tables), and `FeedbackPublic` (same physical database as `Feedback`, meant for a restricted, INSERT-only-on-submissions MySQL user — see `Schema_Reference.md` for the exact grants — used by the public submission endpoints). `PortalPublic` is the same idea for the civilian assessment: same physical database as `Portal`, for a MySQL user with INSERT on `_assessment_answers`, `_submitter_info` and `_private_assessment` and nothing else (no SELECT anywhere), used only by `POST /api/public/civilian-assessments`. It **fails closed**: with no `DB_USERNAME_PORTAL_PUBLIC` set it borrows Portal's credentials only when `APP_ENV` is `local` or `testing`, and has none anywhere else, so a server without the restricted user refuses civilian submissions rather than making them with full access. Never use it to read, and never give that endpoint's validation an `exists:`/`unique:` rule (they SELECT). `CivilianAssessmentTest`'s can't-read check runs only when a separate user is configured. In practice, **every table including `users` currently lives on the `Portal` connection** — migrations were originally run with `--database=Portal`, which overrides the connection for any migration that doesn't set its own, and `User.php` now explicitly declares `protected $connection = 'Portal'` to match that reality (it didn't used to, which would have made any real login attempt query the wrong, unreachable `mariadb` connection). Every Portal-connection model extends `BaseModel` except `User` (which extends Laravel's `Authenticatable` but still declares `$connection` manually) — `BaseModel` throws at boot time if a subclass omits `$connection`, so that mistake surfaces immediately rather than silently querying the wrong database. When adding a new Portal-connection model, follow the existing pattern (extend `BaseModel`, set `$connection`, use `HasUuids` with a `uniqueIds()` override for the uuid-keyed tables — primary keys here are custom-named, e.g. `AssessmentDocID`, `DocumentID`, `SubmissionID` — not `id`; the auto-increment tables like `users`/`agencies`/`law_enforcement_agents` don't need that).

A fifth and sixth connection exist: `Content` (events, newsletters, event categories and `content_files`, the uploaded-file blobs) and `ContentPublic` (same physical database, intended for a restricted SELECT-only user that **does not exist in any environment yet** — see `Filament_CMS_Design.md` §6.5). `Content` is live and migrated, and the public read endpoints (`GET /api/public/events` and `/newsletters`) query through `ContentPublic` — which currently carries root credentials, so creating the SELECT-only user is a `.env` change with no code change.

**See `Schema_Reference.md` at the repo root for the full current schema** (ER diagram + table-by-table notes) — it's kept in sync with `database/migrations/*.php` and is much easier to read than the migration files themselves. Regenerate it after schema changes rather than trusting this file's prose to stay current.

**Always migrate with `--database=Portal`, regardless of what a migration actually targets.** Portal's `migrations` table is the single canonical ledger for every migration in this project, even ones whose `Schema::connection('Feedback')->...` call routes their DDL elsewhere. Running `migrate --database=Feedback` (or any other) against a database whose own `migrations` table is empty makes Laravel try to replay the *entire* migration history into it, not just the ones meant for that database — this happened once while building the Feedback schema and had to be cleaned up.

**Sensitive columns are encrypted before they reach the database** (Finishing Touches item 14, 2026-10-27; `App\Support\SensitiveData`). Encrypted: every victim and offender detail on both assessments (names, sex, dates of birth, relationship and its Other text, safe phone), `_submitter_info`'s contact details, a resource request's name, email, phone and message, the change log's `PreviousValue`/`NewValue`, and `follow_up_entries.Note`. Plain: the 11 answers, ids, times, `submitted_by`, edit reasons, service feedback and everything on `users` (passwords are hashed; staff emails stay plain because sign-in looks them up). Each model lists its columns in an `ENCRYPTED` constant and uses `App\Models\Concerns\EncryptsSensitiveFields` (Laravel's `encrypted` cast; phone formatting goes in `phoneNumberFields()`, never an `Attribute` mutator, which would skip the cast). **The key is `DATA_ENCRYPTION_KEY`, never `APP_KEY`** (`Model::encryptUsing()` in `AppServiceProvider`), with no fallback: without it every read or write throws (`App\Support\MissingDataKey`). `php artisan data-key:generate` creates it and never replaces one; old keys go in `DATA_ENCRYPTION_PREVIOUS_KEYS`. Losing the key loses the records. **The database can't search, sort, group or filter these columns**, so: table search uses `->searchable(query: App\Filament\Tables\EncryptedColumnSearch::query(Model::class, [...]))`, the name filters `AssessmentFilters::encryptedTextContains()`, both decrypting the viewer's `visibleTo()` rows in PHP (`App\Support\EncryptedSearch`); Analytics decrypts sex, DOB and relationship for the date range (`AssessmentStats::people()`). Never `->searchable(['EncryptedColumn'])`, `where()`, `orderBy()` or `groupBy()` on one — it quietly matches ciphertext. A raw query-builder write must `SensitiveData::encrypt()` itself, and tests find rows with `encryptedRows()` (`tests/Pest.php`). `AssessmentEditor` compares decrypted values (`getAttribute`/`getOriginal`), never `getDirty()`'s ciphertext. A new sensitive column needs the model constant, a migration that changes it to `TEXT` and encrypts existing rows (like `2026_10_27_120000_encrypt_sensitive_columns`), and an entry in `SensitiveDataEncryptionTest`'s migration check.

**Time zones: store UTC, show Eastern** (`App\Support\Timezones`). The app is UTC (`config/app.php`) and every database connection is pinned to UTC (`'timezone' => '+00:00'` in `config/database.php`, deliberately not an env value), so MariaDB's `NOW()` / `useCurrent()` and Laravel's `now()` agree on every machine — before that pin, the database used each developer's own time zone and the same moment was stored differently on different machines. Anything shown to a person converts to `Timezones::DISPLAY` (America/New_York): `->timezone(Timezones::DISPLAY)` on a Filament `dateTime` column/entry or `DateTimePicker`, `->setTimezone()` on a hand-formatted Carbon (`ChangeHistory`, the assessment-record view). **Never on date-only values** (dates of birth, issue dates): Filament's `->date()` converts too and would show the day before. Date filters turn a picked Eastern day into a UTC range (`Timezones::dayStartUtc()`/`dayEndUtc()`, used by `AssessmentFilters::dateRange()`). Event `starts_at`/`ends_at` are `DATETIME` and already followed this rule. Migration `2026_10_08_140000_restore_utc_for_timestamps_written_by_laravel` repaired values Laravel wrote under the old per-machine session (run it right after pulling the change). `TimezoneTest` covers it.

**Migrations vs. the live dev database can drift.** Laravel's `migrations` table only tracks which migration *files* have run by name; editing an already-applied migration's contents doesn't retroactively change a database that was migrated before the edit. If you change a migration that has already run somewhere, that environment needs a deliberate `migrate:fresh --database=Portal` (or a new migration), not just a re-run of `migrate`. This bit the project once already — the dev database was rebuilt from scratch to match the migration files, and as of this schema pass it's confirmed reconciled — but it's a recurring risk any time an already-applied migration gets edited, not a one-time fix. If in doubt, check with `php artisan migrate:status --database=Portal` rather than assuming the live schema matches `database/migrations/*.php`.

### The assessment tables are linked, not independent
Two parallel assessment paths share the same `_assessment_answers` table (11 risk-indicator booleans): `PrivateAssessment` (public/anonymous submissions, `belongsTo` `SubmitterInfo` via `SubmissionID` for optional contact info) and `LawEnforcementAssessment` (authenticated law-enforcement submissions, `belongsTo` `User` via `submitted_by`). See `Schema_Reference.md` for the full relationship diagram. **The civilian flow** is the website's `src/app/assessment/AssessmentContent.js` → `submitAssessment()` in `src/app/lib/assessment.js`: everything stays in the page until Submit, then goes in **one** request to `POST /api/public/civilian-assessments` (`PublicCivilianAssessmentController`, validated by `App\Http\Requests\Public\CivilianAssessmentStoreRequest`), which writes the answers, the submitter (only when reporting for someone else and declining anonymity; refused otherwise) and the victim/offender record in one `PortalPublic` transaction, generates every id itself, and returns only `{ message }`. Throttled `10,1`. `CivilianAssessmentTest` covers the endpoint; `tests/assessment.spec.js` (Playwright) covers what the page sends. The page opens with a **Confidentiality Notice that can't be dismissed** (`Modal` with `dismissible={false}`: no X, no click-outside); "I understand, continue" is the only way on. The Esc key is the website's Safe Exit shortcut and leaves the site entirely, which is intended; keep the Safe Exit button clickable above every modal. The notice (rewritten 2026-10-22, team plan task 24) says Harbor Safe follows up every submission at the safe phone number and nothing is saved until Submit; keep it, and the questions intro's "Nothing is saved until you submit", true to what the flow does. **Before Submit, the review shows everything entered and all 11 answers** (team plan task 31), with an Edit button per section and a Change button per answer that come straight back to the review ("Return to review"); answers are shown plainly, with no risk colouring or score, since the reader may be the victim. Submit stays disabled until the safe-phone box is ticked ("I confirm {number} is a safe phone number to contact" — the officer wizard's check, in Harbor Safe's own wording for the public); changing the number unticks it, and it is never sent. `tests/assessment.spec.js` covers it. **The law-enforcement flow** is the Filament page `App\Filament\Pages\NewAssessment` (`/police/new-assessment`), which creates the `AssessmentAnswers` row and the `LawEnforcementAssessment` row itself, in one `Portal` transaction, with `submitted_by = auth()->id()` — no API round trip. Its Review & Submit is laid out like the civilian review (2026-10-24): an Edit button per section and a Change button per answer, coming straight back; once the last question is answered (`NewAssessment::$reviewReached`), each step's Continue reads "Return to review" and, after the step's own validation, jumps back to the review (`backToReview()`, an `afterValidation` hook that dispatches the wizard's `next-wizard-step` event and `Halt`s), and any answer returns to it (`answerQuestion()`, `editAnswer()`). Question 1 has a Back to the intro step, since the wizard's own Back row is hidden on the questions step. Unlike the civilian review it keeps the red yes highlighting and count, and its own checkbox wording. `NewAssessmentReviewTest`. Its question wording is duplicated in `NewAssessment::QUESTIONS` and `website/frontend/src/app/lib/lethality-questions.js`; change both together (`LethalityQuestionsTest` fails if they differ). **"Relationship to victim" is a fixed list** (`App\Enums\OffenderRelationship`, roadmap Phase P): records store a code, `other` carries a typed detail in `OffenderVictimRelationshipOther`, and both APIs validate with `OffenderRelationship::validationRules()`. The panel uses `App\Filament\Assessments\RelationshipFields` (wizard and officer Edit), the civilian form fetches the options from `GET /api/public/relationships` (no JS copy), and every display goes through `OffenderRelationship::display()`. Changing an option is a code change on purpose — agree it with Harbor Safe; labels capitalise every word. `RelationshipListTest`. If you touch field names on any assessment-related table, update the migration, the model's `$fillable`, the `NewAssessment` wizard fields (and the officer Edit form, `AssessmentEditForm`), and the civilian payload (`CivilianAssessmentStoreRequest`, `PublicCivilianAssessmentController`, `website/frontend/src/app/lib/assessment.js`) together — they've fallen out of sync with each other more than once.

### Auth: Filament login; access decided in code by `users.role`, never by a permissions screen
`users` has `role` (a native `App\Enums\UserRole` enum: `law_enforcement`/`secretary`/`admin`/`police_admin`/`super_admin`, cast — not a raw string; `UserRole::label()` is how the panel names each one), `is_active`, `first_name`/`last_name` (50 characters each, the source of truth for a person's name) alongside `name` (kept as a real column because tables search and sort on it, and always rebuilt as "First Last" by `User::booted()` — never write it directly), and Fortify-style 2FA columns that **nothing uses** — Fortify isn't installed, and Filament's built-in MFA expects its own column names (`app_authentication_secret`, `app_authentication_recovery_codes`); `law_enforcement_agents` holds badge/agency data for officers *and* police admins (1:1, keyed by `user_id`; `User::officerIdentity()` reads it with the agency name, `User::agencyId()` reads just the agency — a police admin's row exists purely to carry that link); `law_enforcement_assessment.submitted_by` is a real FK to `users.id`. **Sign-in is Filament's login** at `/login` (`App\Filament\Pages\Auth\Login`, Filament's authentication with the old Next.js page's look), gated by `User::canAccessPanel()` (`is_active` plus a valid role); each panel page gates itself with `canAccess()` on `role`. The API has **no signed-in routes at all** (team plan task 29 removed them; see Routing): staff work only in the panel. **In the panel, law-enforcement assessments are governed by `App\Policies\LawEnforcementAssessmentPolicy`** (registered with `Gate::policy()` in `AppServiceProvider`): hand-written, `users.role` plus `submitted_by` ownership plus the police admin's agency. Every write method returns `false` except `update()`, which allows the submitting officer **or** an active police admin of the submitter's agency (`managedAgencyId()` plus `visibleTo($user)->whereKey(...)`, which covers their officers' and their own submissions) — §5 rule 1, widened deliberately for the same agency only (team plan task 7); admin stays view-only. **Every edit goes through `App\Services\AssessmentEditor`**, which writes one `assessment_edits` row (who, when, required reason) plus one field-level row per changed column in `assessment_change_log` / `assessment_answer_change_log`, in one `Portal` transaction. `LawEnforcementAssessment` and `AssessmentAnswers` throw on any `update()` outside the editor (`EditedOnlyThroughAssessmentEditor`), and the edit and log models are append-only (`AppendOnly`) — so test cleanup and any other removal must use the query builder, never Eloquent deletes. Who sees which rows is the `LawEnforcementAssessment::visibleTo($user)` query scope — admin everything, police admin its own agency's officers' submissions (nothing without an agency), officer its own — and the policy's `view()` and both assessment screens' `getEloquentQuery()` all go through it. **Police admins are agency-scoped. Never widen police_admin to see all agencies or add a screen that skips LawEnforcementAssessment::visibleTo(). See Filament_CMS_Design.md §5 rule 5.** `laravel/sanctum` was removed with the signed-in API routes, and its empty `personal_access_tokens` table dropped by migration `2026_10_22_120000` (the migration that created it stays, like every migration that has run).

The old placeholder Next.js login (`app/api/auth/login/route.js`, which accepted any credentials and set `session=dev-token`) and `proxy.js` are deleted — don't resurrect either.

**Every screen lists what it lets anyone do, and refuses the rest** (decided 2026-10-24, replacing the Shield plan). Who may *open* a screen is its `canAccess()` on `users.role`, pinned by `PanelAccessTest`. What they may *do* there is a second, separate rule, because Filament asks each screen before every built-in button (Create, View, Edit, Delete, bulk delete, restore, replicate, reorder) and by default answers "allowed" when a model has no policy, so a Delete button added to a read-only screen would have worked for everyone who could open it. So every screen answers explicitly: `App\Filament\Concerns\AllowsOnlyListedActions` (the screen lists its actions in `allowedActions()`, with an optional per-row `allowsRecord()`; everything else is refused, and nothing for someone who can't open the screen), or the same rule written out in `getAuthorizationResponse()` (Accounts, Officers, Agencies), or `LawEnforcementAssessmentPolicy` (both law-enforcement assessment screens, every method written out). Overriding `canDelete()` and friends is **not** enough: Filament's buttons call `getAuthorizationResponse()` directly. The panel runs in **strict mode** (`->strictAuthorization()` in `StaffPanelProvider`), so a new screen with no rules is an error rather than a yes. `tests/Feature/Staff/ActionAccessTest.php` lists every screen's actions and fails on a screen that allows more, refuses its own list, or isn't listed. A new screen: add the trait and its list, then add it to that test. Custom actions (`Action::make(...)`) aren't covered by this — each must check permission itself (`->visible()`/`->authorize()`, and again in its service on save). Access is changed by a developer in code, never through a screen: the project will be handed over, and nobody running it should be able to widen access from inside the panel. `submitted_by` is what "law enforcement sees only their own submissions" checks against.

### Staff panel (Filament) — officer screens and content management built
Every staff dashboard lives in one Filament v5 panel inside `portal/backend`, behind Filament's own login. Only the civilian assessment lives outside it, on the public website (`website/frontend/src/app/assessment/`). Five sidebar groups (Police Admin is described with the Officer Portal below, Reports with Analytics further down), each with its own address space:

- **Content management** (admin, secretary) — three Filament **clusters**, which render their resources as tabs across the top of each page: `Content` (`/content/{events,newsletters,categories}`), `Submissions` (`/submissions/{service-feedback,resource-requests}`, statements from the public, so **never edited** — resource requests are read-only, and service feedback's one addition is **New feedback form**, for admin and secretary to fill a form in themselves (typically one that arrived on paper, though the screen deliberately never says so): validated by `ServiceFeedbackStoreRequest::fieldRules()` (the website's own rules), saved by `ServiceFeedback::recordStaffEntry()` with `Source = staff` (shown as a "Staff" badge), `EnteredBy` and the date and time entered, plus an optional scan stored in `feedback_scans` and served only to admin/secretary by `FeedbackScanController`, never through `/files/{file}`; a mistyped entry is deleted and re-entered, and its scan goes with it — `StaffFeedbackEntryTest`. The form's date-and-time field is entered in Eastern and saved as UTC, like everything else — see **Time zones** below. Service feedback also has an **Export** button (Excel or PDF, for grant reports; team plan task 34): it exports whatever the table's applied filters and search leave — every page, one form per row — by reading the table's own query, so the date-submitted and service filters are set in the table first. **The file holds only what each form holds: the day submitted (Eastern, a real date cell in Excel), service, rating and comment** — no source, staff names, scan, time of day, filters or export date (AS, 2026-10-20; Harbor Safe knows comments are included and can drop that column in Excel). Built by `App\Services\ServiceFeedbackExport` (openspout for .xlsx, dompdf for PDF); **deliberately not logged**, unlike assessment PDFs, since feedback is data collection — `ServiceFeedbackExportTest`.) and `Form options` (`/form-options/{services,resource-types,counties}`, the dropdown choices behind the public forms, sharing one `LookupResource` base). Plus `Accounts` (`/accounts`, `Resources/StaffAccounts/`, **admin and super admin**): admin creates, edits and deactivates **secretaries**, never any other role and never itself; super admin does the same for **every role, other super admins included** (so ownership can pass on when one leaves), never itself — and since nobody manages their own account, the last active super admin can't be switched off. Who may manage which roles lives in one place, `StaffAccountResource::manageableRoles()` — extend that map rather than adding checks elsewhere. A creator with one manageable role sees it in a greyed-out, never-sent Role box (`AccountFormSections::fixedRole()`; the role is forced on the server); super admin picks one from a Role dropdown, re-checked against `manageableRoles()` on the server, and police admins and officers also get an **Agency** (must exist) and officers a **Badge number**, saved on their `law_enforcement_agents` row in the same Portal transaction (a police admin's badge is stored empty; `displayBadge()` shows "Police admin"). Who works which kind is `FollowUpKind::workedBy()`, which reuses `NewSubmission::alertedRoles()` (admins: assessments; secretaries and admins: resource requests); `FollowUp::visibleTo()` scopes every query by it. **Officers and police admins never see follow-up information, on any screen or PDF.** Migration `2026_10_20_130100` opened Needs follow-up for every existing form with its real submission time, counting past reminders as sent. Tests delete follow-ups before forms (`cleanupFollowUps()` in `tests/Pest.php`). `FollowUpsTest`.

**Pop-ups and table menus** (team plan task 5). No pop-up closes when someone clicks outside it — only its X, Cancel or Esc — set once for the whole panel by `ModalComponent::closedByClickingAway(false)` in `AppServiceProvider`, so don't turn it back on per action (`PopUpTest`). In `theme.css`, `.fi-ta-ctn` clips its contents only when the table has no toolbar, as Filament does: an unconditional `overflow: hidden` there cut the filter menu off inside tables of two rows or fewer. Rows stay inside the rounded corners because `.fi-ta-content-ctn` rounds its own bottom to the border's radius.

The panel's look (dark sidebar, `#5C0F8B`, Tailwind gray, Nunito/Montserrat, no topbar, no dark mode) comes from the custom theme plus `StaffPanelProvider`. **Sessions: 15 idle minutes for every role, ended when the browser quits** (`SESSION_LIFETIME=15`, `SESSION_EXPIRE_ON_CLOSE=true`, and both are also the fallbacks in `config/session.php`, so a missing value can't mean two hours; check your own `.env`, which used to say 120). The officer Home's "Session logs out after N minutes of inactivity" reads N from that value. Because the server only notices expiry on the next request, `resources/views/filament/partials/idle-logout.blade.php` (a `SCRIPTS_AFTER` render hook, signed-in users only) reloads an idle page just after the deadline so it lands on `/login` instead of leaving victim details on screen; its clock restarts on every page load and Livewire request, shared across tabs. **Two minutes before the deadline it warns** ("You'll be signed out soon", a live countdown, **Stay signed in** and **Sign out now**; Filament's own pop-up, which can't be closed by clicking outside or Esc). Stay signed in posts once to `POST /session/keep-alive` (`KeepSessionAliveController`, behind `EnsureStaffPanelAccess`: a 204 that restarts the session's clock, or the sign-in redirect if it has already ended, so it can never revive an expired session); activity or Stay signed in in one tab closes the warning in the others. Only that button may call it — never a timer. Never add `wire:poll` or polling to a panel page without accounting for this: each poll is a request and would keep an unattended session alive forever. It is an *idle* timeout, not a re-auth on every navigation (see `Filament_CMS_Design.md` §12). `SessionTimeoutTest`. **An unfinished officer assessment survives the idle logout, in the browser tab only** (`App\Support\AssessmentDraft`, settled with Harbor Safe 2026-10-24; officers and police admins alike): `resources/views/filament/pages/new-assessment/draft.blade.php` saves the wizard to the tab's **sessionStorage** (never localStorage), AES-GCM-encrypted in the browser under the person's own key (`AssessmentDraft::keyFor()`, hex, written only into the New assessment page; user id and save time bound in), on typing, answers, steps and round trips, and the idle logout waits for that save before reloading (`hs-before-idle-reload`). Signing back in, New assessment offers **Resume** / **Discard it**; `NewAssessment::restoreDraft()` takes back only the wizard's own fields (never `SafePhoneConfirmed`, which is asked again) and Submit validates as usual. Wiped on Submit (`hs-assessment-draft-clear`), Discard and Sign out; dropped after `LIFETIME_MINUTES` (2 h) or when someone else signs in to the tab (`filament/partials/assessment-draft-guard.blade.php`, every page). **Never add a drafts table or send the unfinished form to the server**: a police admin can't finish an officer's form on purpose (they Edit it after submission). Needs https (Web Crypto); without it nothing is saved. `AssessmentDraftTest`. Five roles: `law_enforcement` (own submissions only; submits and edits its own), `police_admin` (provisions its own agency's officer accounts, views its own agency's law-enforcement submissions and change logs, submits its own assessments and edits any in its agency — §5 rule 1, same agency only), `secretary` (content and submissions, never assessment PII), `admin` (edits content and the public forms' dropdown options, views submissions, views **all** civilian and law-enforcement assessments, creates **secretaries only** — **not** the officer portal, never officers, never edits an assessment; admin is deliberately not a superset), and `super_admin` (admin's access plus Agencies and creating every role, other super admins included; view-only on assessments, no Officer Portal). Police admins and admins are created by super admin only.

**Sign-in and landing.** Everyone sees the same login screen at `/login`, a neutral address at the site root shared by every role (the panel is served from the root; old `/staff/...` links redirect to their new address via `routes/web.php`). Where they land is decided in exactly one place, `App\Filament\StaffLanding` — super admin/admin/secretary to the Follow-ups queue, officers/police admins to the officer portal — consulted by both `StaffLoginResponse` (after sign-in) and `RedirectStaffHome` (opening `/staff` directly). Don't reach for `$panel->homeUrl()`: it only sets the sidebar brand link and does not affect either redirect.

**Uploads are database rows, not files on a disk.** Event images and newsletter PDFs live in `content_files` on the `Content` connection, written through `App\Filament\Forms\Components\DatabaseFileUpload` and served by `ContentFileController` — publicly at `/api/public/content-files/{file}` (only while a *published* event or newsletter points at the file) and to staff at `/files/{file}`. Two rules to respect: `App\Models\ContentFile` has a global scope excluding the `contents` blob from every query (use `->contents()` for the bytes, never the attribute), and uploads are capped at 4 MB (images) / 8 MB (PDFs) because `max_allowed_packet` is 16 MB and caps a single row in both directions. **Those caps need php.ini to cooperate** — stock `upload_max_filesize` is 2M, which makes PHP discard the file before Laravel runs, so the failure looks like a broken panel rather than an oversized file; this project needs `upload_max_filesize = 8M` and `post_max_size = 12M` (`PORTAL_SETUP.md`). `DatabaseFileUpload::effectiveLimitKb()` clamps the advertised limit to whatever PHP will actually accept, so the helper text cannot over-promise. `events.image_path` / `newsletters.file_path` are kept but unused, so a move to R2/B2 stays a config change.

**The access matrix is enforced by test.** `tests/Feature/Staff/PanelAccessTest.php` writes §5 out as a table and asserts each role reaches exactly its own row — it exists because `Police`, `MyAssessments` and `SearchRecords` (since removed) had all quietly granted `admin`, which put the whole Officer Portal in an admin's sidebar. If you change who sees what, that file is the place it has to agree. Two gotchas for authenticated tests: cleanup sweeps on the fixed `peststaff` prefix (so a fatal-killed run self-heals, but don't run these in parallel), and `UploadedFile::fake()` is unusable here — `fake()->image()` needs GD, which isn't installed, and `fake()->create()` writes zero bytes while reporting a size. Use `Illuminate\Http\Testing\File` with a real `tmpfile()`.

### Routing
`bootstrap/app.php` only registers `routes/web.php`, `routes/api.php`, and `routes/console.php`. **The JSON API is only the public website's surface** — no signed-in routes. The six per-table `apiResource`s (`/assessments`, `/private-assessments`, `/submitter-info`, `/law-enforcement-assessments`, `/law-enforcement-agents`, `/agencies`) and `GET /api/user` sat behind `auth:sanctum` with nothing able to issue a token, and were removed with their controllers in team plan task 29 (one of them, `update()`, took `submitted_by` from the request). Staff screens belong in the panel, never here; `tests/Feature/ApiSurfaceTest.php` lists every `/api` route and fails on a new one, a signed-in one, or an unthrottled public write. Besides `GET /api` (a health message), a `Route::prefix('public')` group exposes a deliberately narrow surface for the public website: `GET /api/public/{services,resources,counties,relationships}` and throttled (`throttle:10,1`) `POST /api/public/{service-feedback,resource-requests,civilian-assessments}`. The form controllers route through the restricted `FeedbackPublic` connection, never the full-access `Feedback` one, and the civilian assessment through `PortalPublic`, never `Portal`. CORS (`config/cors.php`) allows only `WEBSITE_URL` (plus localhost:3000 when `APP_ENV=local`), GET and POST, and the `Content-Type`/`Accept` headers. Also in that group: `GET /api/public/events` and `GET /api/public/newsletters`, which serve published website content shaped by `PublicEventResource` / `PublicNewsletterResource` to match what the Events & News page consumes — **those two resources are the contract**, asserted key-for-key in `tests/Feature/Public/ContentEndpointsTest.php`, and `website/frontend/src/app/lib/content.js` has to change with them. Both read through `ContentPublic`; `PublicEventController` joins `event_categories` rather than eager-loading it, because a relation resolves on the *related* model's connection (`Content`) and would bypass the restricted user. Plus `GET /api/public/content-files/{file}`, which streams an event image or newsletter PDF out of the database — and only while a *published* record points at it, since `content_files` has no published flag of its own to consult. Its staff-side twin is `GET /files/{file}` in `routes/web.php`, which is guarded by `App\Http\Middleware\EnsureStaffPanelAccess` rather than `auth`: Laravel's `auth` redirects to a route named `login` that doesn't exist here (sign-in is Filament's), so `auth` would turn an anonymous request into a 500. The same middleware guards `GET /assessments/{id}/pdf` (see Staff panel) and `POST /session/keep-alive` (the idle warning's Stay signed in). No API routes for the change log — it is read in the staff panel only (Logs at `/logs`, and each record's per-row Change log pop-up). The staff panel is served from the site root (Filament registers its routes itself): sign-in at `/login`, content management under `/content`, `/submissions` and `/form-options`, the officer portal under `/police`, and `/` sending a signed-in user to their own area. Everything under `/api` is the JSON API, not the panel; `/staff/{path}` in `routes/web.php` redirects old links. The panel id is still `staff`, so route names stay `filament.staff.*`.
